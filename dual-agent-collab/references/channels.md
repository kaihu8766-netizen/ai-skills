# 评审通道（channels.md）

## 两个通道

| 通道 | 时机 | 用途 | 必填 |
|---|---|---|---|
| `scheme`（事前对齐） | 动手前 | 评审方案：目标、改动点、风险、验收标准、优先级 | `--feature F-xxx` |
| `review`（事后复核） | 完成后、提交/发布前 | 评审产物：是否符合方案、有无缺陷、改进意见 | — |

## 结论词表（评审必须落到这三类之一）

- **通过** → 可动手 / 可提交发布
- **有条件通过** → 列出条件；主 Agent 逐条说明如何满足，或按条件修复后补一次轻量复核
- **拒绝** → 列出原因；修复后以 `--force` 重审同一 topic（或换新 topic）

## Prompt 模板

### scheme（事前对齐）

```
【方案评审（事前对齐）】
目标：<一句话目标>
方案：<改动点/实现路径>
风险与边界：<已知风险、不做范围>
验收标准：<可检查的完成定义>
请评审：1) 方案是否可行、有无更优路径 2) 优先级排序 3) 遗漏的风险。
结论：通过 / 有条件通过（列条件）/ 拒绝（列原因）。
```

### review（事后复核）

```
【完成复核（事后双闸门）】
事前方案：<引用 RV-xxx / F-xxx>
已完成内容：<改动摘要、文件、验证结果>
请独立评审：1) 是否符合事前对齐方案 2) 有无缺陷/遗漏 3) 改进意见。
结论：通过 / 拒绝（列原因）。
```

## 评审纪律

- 评审 Agent **不参与执行**（避免自我确认偏差）；它只基于你给的描述 + 它可读取的证据判断
- **独立性边界**：评审 Agent 只读产物/档案（git、文件、提交 diff），**不共享主 Agent 的推理链、草稿、中间计划**——评审输入是"产物"不是"过程"，这是"独立"的判定标准
- 评审 Agent 能力边界如实记录：只读环境、无联网、可能截断长上下文——评审长文档时拆段发
- 同一 diff 重审用 `--force`；不要把重审当成新评审混入新内容

## 评审状态机

```text
pending（已发起）→ adopted（已批准，可提交/发布）
                 → rejected（已拒绝，修复后重审）
                 → closed（已关闭归档，如已废弃/已合并）
```

- 状态只增不改历史行；状态变更用新行表达（审计可追溯）
- 有条件通过 = pending + 条件清单；主 Agent 逐条说明满足后置 adopted

## 人类裁决与死锁出口

- 人类是最终裁决；评审与主 Agent 分歧时以人类拍板为准
- **人不在场时的默认策略**：可逆动作（改代码、写档案）先按评审结论执行并留痕，留给人类复核；**不可逆动作 BLOCKED 上报**，绝不 fail-open
- 超时：评审调用超时/评审 Agent 不可达 → 重试一次；仍不可达且动作可逆 → 记录"评审不可得"继续可逆部分，不可逆部分 BLOCKED
