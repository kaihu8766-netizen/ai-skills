# 评审强制框架（review-framework.md）

DeepSeek 评审"聪明"的来源不是模型本身，而是**执行方喂料的质量 + 评审被强制遵守的纪律**。本文件是发起评审时必须遵守的强制框架（RV-20260928-07 采纳）。

## 一、评审 prompt 强制模板（五要点 + 三补强）

发起评审时，prompt 必须显式要求 DeepSeek 按以下纪律回答：

1. **逐条核验 + 证据引用**：每条判断必须带证据引用（`路径:行号` 或 commit 短码）；无证据支持的判断不得写成"已核验"，只能写"推理/未取证"
2. **主动反证检查**：构造 1-2 个可能让结论反转的反例并尝试核验（如"改动是否会放宽断言/绕过门禁/泄露数据"）
3. **负向诚实 + fail-closed 默认**：列出未取证清单（未核验 ≠ 不存在）；**取证不到的关键项一律按未核验处理，禁止"看不见即无问题"放行**——无法取证的关键判定必须降级为"有条件/拒绝"
4. **结论三态**：`通过` / `有条件通过`（列出条件）/ `拒绝`（列出原因）；有条件通过 = 执行方逐条说明如何满足后置 adopted
5. **证据喂料（反选择性举证）**：无只读取证工具（evtools）时，执行方把**改动正文/关键文件的原始片段 + 行号**贴进 prompt；摘要仅作背景，且必须声明"省略了什么"——禁止只喂美化后的摘要
6. **上下文注入（预算上限）**：评审前注入最近 2 份 adopted 档案结论 + OPEN_ISSUES/DECISIONS 摘要，**合计 ≤800 字**，放 prompt 开头；超过则只保留最近 1 份 + 关键决策
7. **触发条件（必须唤起评审，不可跳过的类型）**：红线文件改动 / 门禁脚本改动 / 方案与架构决策 / 数据安全相关 / 用户明确要求"讨论"的任何改动

## 二、评审通道与落盘

- 评审必须**落盘**：原始请求/响应 JSON + 索引行（追加式），供事后审计
- 同一 diff 重审用 `--force`；不要把重审混为新评审
- 评审结论为拒绝/条件未落实 → **不得执行该动作**，上报用户拍板（讨论闸门动作约束）

## 三、无 evtools 环境的证据喂料示例

```text
【证据（原文片段）】
文件 scripts/gate_rules.yaml 第 41-52 行：
  max_files: 3
  max_lines: 30
  max_line_chars: 500
  quota_file_lines_7d: 50
  quota_light_commits_7d: 5
【背景摘要】本次改动仅调整 LIGHT 限额（省略了：未涉及红线路径、未改解析逻辑）
```

- 喂原文片段保证 DeepSeek 看到真实内容（反美化）；声明省略项保持诚实。
