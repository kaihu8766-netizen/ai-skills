# 门禁与闸门（gates.md）· 可选高级模式

**默认模式（无 git 仓库）**：靠"讨论纪律 + 轻量档案留痕"兜底——**这是 fail-closed 语义，不是没有兜底**：讨论不是可选项（SKILL.md 讨论纪律），档案必须落盘（light-archive.md），结论三态如实记录。无仓库 ≠ 无约束，只是约束从"机器拒绝"变为"纪律 + 可审计留痕"。

**高级模式（有 git 仓库）**：装 commit-msg 钩子后，"未评审的提交"被**机器拒绝**（协作质量生命线，防自觉失效）。安装：`scripts/install-gate.sh <项目根目录>`（复制 commit-msg 到 `.githooks/` + `git config core.hooksPath .githooks`）。

## Git 提交门禁（commit-msg 钩子，高级模式）

**通用版两闸门（install-gate.sh 装好即生效）**：

1. **闸门 1（ID 引用存在性）**：提交信息必须含合法 ID 引用（`RV-*` / `GATE-*` / `DEC-*` / `ISS-*`）→ 防止"未评审的提交"
2. **闸门 2（RV 存在 + adopted）**：引用的 RV/GATE 必须在评审索引中存在且状态为 adopted（宽容正则：竖线分隔单元以 adopted 开头，容忍空格差异）→ 防止"伪造号/冒用 pending 号"
3. **引导期豁免**：索引文件不存在/为空 → 放行（打印提示）；建立首个评审档案后强制生效（解决"归档本身也是一次提交"的鸡生蛋）
4. **可选 diff_hash 告警（不阻断）**：索引行带 diff_hash 时比对当前 staged，不一致仅 WARNING（提示"评审对象与提交对象可能不一致"）——完整版为阻断校验（见下）

**项目级完整版（高级用法，非通用默认）**：三闸门（ID 引用存在性 + 红线 diff_hash 阻断匹配 + 功能提交需事前对齐 scheme-RV）+ [LIGHT] 轻量通道（限额判定写在 gate_rules 脚本，不能靠自觉）。参考实现：invoice-precheck 仓 `.githooks/commit-msg` + `scripts/trace_gate.py` + `scripts/gate_rules.yaml`。通用版砍掉红线 diff_hash 阻断是为了最小可用；需要"评审对象 = 提交对象"级强保证的项目，升级到完整版。

**索引契约（通用版钩子依赖，格式耦合是实战踩过的坑）**：索引一行一条、UTF-8；状态列写 `| adopted |`（空格差异被宽容，但禁止写成 pending/rejected 冒充）；行内须含"日期-RV号"前缀（如 `2026-09-28-03-`），钩子按该前缀定位；只追加不删历史行。

## 讨论闸门规则（周期自检/定时任务触发时）

按七段执行（比"四条"更完整的实战抽象）：

1. **判定三态**：纯只读且与上次基线完全一致 → 免讨论，记录"无异常"；有状态变化/异常/需决策 → **必须**先与 DeepSeek 讨论（review 通道，落盘）→ 有结论再行动；无法判定 → fail-closed 视为需讨论
2. **基线**：以最近一次成功运行的记录为基线，增量比较；不按"当天"而按"自上次基线以来的增量"
3. **动作约束**：讨论结论为拒绝或条件未落实 → 不得执行该动作
4. **紧急止损白名单**：仅限数据泄露止损/环境故障/安全事件三类可先止损后 24h 内补讨论；止损前留脱敏证据；跨仓改动需例外条款
5. **降级禁止 fail-open**：DeepSeek 不可用时不可逆动作 BLOCKED 上报用户，禁止擅自继续
6. **记录**：每次讨论/自检结果落 DailySummary（问题清单、DeepSeek 意见、待拍板项）
7. **诚实边界**：机制"防遗忘不防恶意绕过"——纪律依赖执行者诚实遵守

## 失败与回滚

- 评审发现致命错误：先修复再提交；已提交的用 `git revert`/`git reset` 回退，回退本身也要引用 RV 留痕
- commit 已过三闸门但事后发现错误：按新 RV 记录缺陷 → 修复 → 重审 → 新提交；**不修改历史 commit**
- 回滚优先级：可逆（代码/文档）→ 立即回滚；不可逆（已发布/已外发）→ 上报人类决策

## 常见坑（实战教训）

- **adopt 追加新序号 ≠ 原 RV 号**：索引按 topic 追加行时，同 RV 会出现多行；钩子按"序号前缀"匹配会取错行 → 钩子应改按**档案 frontmatter 的 RV id 精确匹配**，索引清理冗余行时保留 adopted 行
- **钩子与档案 hash 算法不一致**（排除集/路径不同）→ 同一 diff 两边算出的 hash 不同 → 校验必失败；两边必须共用同一份 EXCLUDE/路径规则
- **索引只追加不删**，但冗余 pending 行会造成误判 → 定期归并（删 pending 冗余、保留 adopted）
- **评审 Agent 无联网**：需要联网核实的事实由主 Agent 先查证后喂给评审，评审只做推理与结构性审查
- **长上下文截断**：评审材料超长时拆段，或只发关键 diff 摘要
- **评审链断点（白名单）**：评审 Agent 只读范围受白名单仓库限制——**技能仓/未挂载路径不可读**；需要评审技能自身或仓外对象时，先把对象镜像进白名单仓（如 `skills-mirror/`）或直接贴进 prompt
- **跨仓共用引擎的死路径（--rules 漏传）**：多仓共用一个 gate 引擎脚本时，`check-scheme`/`check-rv` 等闸门若不显式传 `--rules <本仓规则文件>`，会默认读引擎所在仓的规则文件 → **本仓规则里定义的类恒不命中，闸门被静默绕开（恒跳过）**。排查信号：闸门打印"未命中类，跳过"但本仓规则明明配了该类。铁律：**每个仓的 commit-msg 钩子调用闸门时都必须显式传 `--rules`**，不依赖默认路径
- **规则文件自指逃逸（硬编码锚）**：闸门判据写在 `gate_rules.yaml` 里时，"改这个 yaml 文件删掉触发类"就能绕过闸门——判据与被判对象同一份文件。防法：把"规则文件自身路径 + 钩子文件 + 引擎脚本"硬编码进引擎代码（不随 yaml 被删改失效），改这些文件本身必触发审查；且最好让"规则文件路径"硬编码触发事前对齐层（不止事后 RV 层）
- **scheme 闸门的诚实边界**：commit-msg 只能要求"存在 adopted scheme-RV 档案"，**无法证明方案真在动手前做的**（同 commit 里补档案也能过）；真正的时序由事后审计（scheme-RV 入库时间 vs 功能代码首次提交时间）兜——宣传口径不要说"堵住了事后补评审"，而是"把门槛从补事后 RV 抬到补事前方案档案"
